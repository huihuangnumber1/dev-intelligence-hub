# 自动流程修复与上游设计吸收

## 目标与授权

用户在源码对照审查后要求“修复并吸收”。本次修复已复现的流程缺陷，
补齐自动修复后的内部复审、运行事实与真实测试接入，完成验证并部署。
普通自动 Review、已授权自身 PR 修复、内部岗位交接不增加逐项人工确认。
不自动合并、不关闭 Issue、不恢复用户暂停的 Draft #24674，不重试封存的旧推送。
保留现有账本、Head/授权绑定、完整读取、受控执行与未知结果对账。
本仓库已有大量未推送提交，只提交本次改动，不推送整条历史。

源码基线：`5bd365e5002e0d865ee4b3610346f6c57bd9d264`。
参考 Retinue `72aff265c4dd4f01992f54298ca9bdaf5e04dafc` 的执行凭据、终态补记和交棒；
参考 agent-feishu-bridge `869fd69e27384040019fbf69505a336151ed9159` 的线程请求隔离与活动事件。
独立实现，不复制上游源码，不采用未确认停止就释放执行占用的处理。

## 实施单元

### U1：旧等待接续与 Review 回执恢复

仅对已经交付、无外部副作用的旧 `wait_condition` 意图，在新 Head 已接受且
其他参与者均可安全结算时 supersede，激活最新来源。外部未知结果仍阻塞。
Review handler 在恢复丢失的 downstream 引用时，先按内容绑定的确定 ID 查找
已有确认；已完成回执不因当前授权变化降级，也不重新发布。
已有跨来源复审根被这种误记阻塞时，凭精确完成回执和记录绑定正常结算。
Files：work-ledger PR cutover/source/settlement、github-review-proposal-handler、对应测试。

### U2：模型等待、执行记录与有限并发

排队预算与模型执行预算分离，等待模型不得显示成已经启动。
持久化有界、无对话正文的执行凭据，覆盖启动、最近活动、终态和恢复后的未知状态。
吸收按实体/线程隔离的排期方式；并发必须有上限，同实体保持串行，取消/reap
和原生 home 保护必须成立。真实 Windows 双任务验证前不直接打开未经验证的并发。
实体排队键与授权隔离的会话键分开；岗位预领取和直接代码任务须对同一 PR 串行。
执行凭据写入失败须保留待写元数据，并允许存储恢复后重试。
Files：native provider、App Server runner、task-run registry/view、task-runs UI及对应测试。
共享配置与 composition-root 由主执行者集成。

### U3：修复发布后的内部复审

推送确认成功后生成持久化、Head 绑定且幂等的内部 PR 工程师交接。
交接失败保留待恢复记录；重启补记交接而不重放推送。
研发 PR 开发工作不能用直接 `complete` 绕过复审；已有修复须带代码与验证证据交接。
内部自身 PR 复审不冒充 GitHub 自我批准或外部人员已收到通知。
原始反馈须在修复前保存完整、摘要绑定的快照；内部复审须分页读完原反馈和当前改动。
旧记录只允许凭严格匹配原摘要的完整内容恢复，不使用截断的最新评论代替。
Files：automatic-own-pr-repair、role-decision-engine、相关新增交接模块和对应测试。
共享配置、composition-root 及全局文档由主执行者集成。

### U4：真实测试执行接入

接入配置拥有、版本绑定的本机 Windows 固定测试资产，模型只能请求既定 profile。
执行保留源码版本、实际 Windows 进程/执行身份、日志与真实测试统计，不伪造 Docker 身份。
构建产物写入独立副本；取消和超时须确认进程结束。仅编译/环境检查不能记为单元测试通过。
实际启用当前机器可执行的 OCT/Picasso 回归；桌面或硬件仍需实机证据，不冒充已覆盖。
Windows 测试使用 LPAC 系统隔离，实际令牌须证明 AppContainer、Low 完整性及
禁用 ALL_APPLICATION_PACKAGES。只允许写本次源码副本和临时目录，固定程序、
资产与摘要绑定的复制资源只读，宿主租约和服务数据不授予访问，不开放网络能力。
确认进程停止并保存执行证据后回收大副本与隔离 profile。Picasso 使用既有 Docker
隔离执行 Linux 固定资产，不为兼容当前 Windows Node 管道而扩大宿主权限。
Files：code-executor/configuration 合约、受控执行器、测试 runner、相关测试。
配置激活、共享装配和产品级验收由主执行者处理。

预算绑定实际激活而非仅 accepted 的来源版本；在 source 内持久保存偏移，
保留累计领取次数。旧格式只凭完整保留证明，在正常 CAS 领取中封存预算；
日志裁剪不改变当前 Head 的失败预算，不因此放宽旧 blocked 根的自动解除。

## 验证契约

现场验收补充以下完成条件：新 Head 的决策预算独立计算，但保留累计领取次数与旧历史；
已被忽略且未改变权限的来源观察不能改写已完成根或阻塞后续入账；历史 Review 回执
按保留的原授权修订精确结算。正常配置切换造成的明确准入拒绝，在确实排空后不误报
停服失败，未知状态、混合错误及未确认停止仍保持屏障。已记录的 owner 历史发布允许
凭唯一受控提交、当前远端 Head/作者和完整原反馈建立独立观察来源，自动交接内部复审；
该来源不得伪造已完成的确认队列回执或重放封存推送。

每项行为先观察失败用例，再实现并运行相关回归。跨服务流程使用真实账本、
确认队列或执行器组合，不用整个执行器的成功替身代替协议验证。

- 旧 Head 等待、新 Head 冲突解除、重复巡查和重启最终可领取最新 Head；未知外部动作仍阻塞。
- Review 已发表且 downstream 丢失、授权变化时恢复同一完成回执，发布次数仍为一。
- 排队超过模型预算不会造成从未启动的模型超时；状态区分 waiting_model/running。
- 运行结束/重启能看到有界执行凭据；暂停、取消和补充要求屏障保留。
- 修复推送后恰有一次内部复审交接；重启、丢回执、变更 Head、禁用自动策略有确定结果。
- 真实固定测试 profile 有绑定日志和测试结果；环境不可用与产品失败明确区分。
- 独立简化与代码审查完成；部署后核对运行源码、配置、#6526、#24764、#24232及受保护 Draft。

## 完成标准

上述单元实现并通过相关检查；正常服务维护流程部署，实际状态和持久回执验证通过。
已授权可执行工作继续按系统规则推进，不以手改状态、删除历史或手动插队代替修复。
未具备的设备/样本验证明确记录为未覆盖，不以预检代替产品验收。
